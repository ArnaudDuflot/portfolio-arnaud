## The premise

When I sat down to build my portfolio, I had two realities to face:
1. I had **never built a website**. Not one. Not even a Wordpress.
2. I wanted the site to be one of the strongest entries in the portfolio itself — because if I can't demonstrate my Product Ops method on my own personal infrastructure, why would anyone trust me to do it on theirs?

So I treated this site as a case study in real-time. The same way I'd attack any operational problem: **decompose into dimensions, pick the right answer for each, document the trade-offs, ship.**

Here are the 11 dimensions I attacked, and how I thought about each.

---

## 01. Technology

**Decision**: HTML/CSS/JS vanilla for v1 → Astro + MDX for v2.

**The trade-off**: I considered Next.js (industry standard, React-based), Astro (modern static-first, lighter), and pure vanilla (zero dependencies). For a content-driven site with no complex interactivity, **React/Next.js is overkill**. Astro ships ~0 JavaScript by default. That matters for the next dimension.

## 02. Robustness

**Decision**: Static site generation. No backend, no database, no auth.

**The trade-off**: A static site can't go down because of a server crash — it's just files on a CDN. The fragility is moved entirely to my deployment pipeline (Netlify) and my Git history. Both have 99.99%+ uptime tracks.

*To be expanded with my reliability reasoning.*

## 03. Scalability

**Decision**: CDN-served static site (Netlify).

**The trade-off**: I could serve this site to 1M visitors a month at zero marginal cost. If I ever needed dynamic features (auth, comments, etc.), I'd add them as serverless functions — but I won't pay for capacity I don't use.

*To be expanded with capacity planning notes.*

## 04. User load (Performance)

**Decision**: Core Web Vitals as a north-star metric.

**Approach**: Astro's island architecture, image optimization, no client-side JavaScript framework, system fonts as fallback, modern image formats.

*Target: 95+ Lighthouse score on all four metrics.*

## 05. Interoperability

**Decision**: Standards-based markup (semantic HTML, ARIA labels, Open Graph metadata, JSON-LD).

**Why it matters**: The site needs to render correctly in every browser, work with screen readers, look right when shared on LinkedIn/Twitter/Slack, and be indexable by Google. None of these are optional.

*To be expanded.*

## 06. SEO

**Decision**: Server-rendered HTML at build time + structured metadata + sitemap.

**Approach**: Each project page has its own URL, its own title, its own meta description. The site has a sitemap auto-generated. Internal linking between projects creates topical authority.

*To be expanded with keyword strategy.*

## 07. Design

**Decision**: Dark Forest direction. Forest green accent on near-black background, with gold/ochre for warmth.

**Reasoning**: My positioning is "grounded, thoughtful, builder." The visual language needed to reinforce that — not contradict it with corporate LinkedIn blue. Dark Forest signals premium without arrogance.

**Identity**: Wordmark "Arnaud Duflot" in Fraunces serif, with a small green dot as signature.

*To be expanded with the full design system.*

## 08. Maintainability

**Decision**: MDX-based content. Each project is a Markdown file with frontmatter.

**Why it matters**: Adding a new project doesn't require touching HTML, CSS, or JavaScript. I write a `.mdx` file, commit, push, and the build pipeline does the rest.

*To be expanded with my content workflow.*

## 09. Observability

**Decision**: Netlify Analytics + (planned) Plausible or Umami for privacy-respecting analytics.

**What I want to know**: Which projects get read all the way through? Where do visitors come from? What's the bounce rate by source? Where does the funnel break?

*To be expanded once I have data.*

## 10. Analytics

**Decision**: Treat the site as a funnel. Top of funnel = visitor lands. Middle = reads a case study. Bottom = copies my email or downloads my CV.

**Goal**: Identify which case studies convert visitors into conversations. Then double down on those.

*To be expanded with conversion tracking setup.*

## 11. Content creation

**Decision**: Five case studies at launch, more added quarterly.

**The friction I'm solving for**: most portfolios are either too thin (no detail) or too thick (TL;DR overload). My target: each case study should be a 5-7 minute read that delivers the *thinking* behind the work, not just the screenshots.

## What this case study is meant to demonstrate

Look at the structure of this page. Eleven dimensions, each with a decision, a trade-off, and a path for expansion. That structure is exactly how I approach any operational problem — whether it's a portfolio website, a translation pipeline, or a support flow.

The site you're reading is itself the proof.
